# إعادة المراجعة بعد تحديث أدلة البراند

## تعريف المهمة قبل التنفيذ

المستخدم صاحب براند عنده SWOT واستراتيجية وبوستر محفوظون، ويعيد استكشاف الموقع. عند حفظ بروفايل جديد يحتاج يعرف أي نتائج تحتاج مراجعة ويقدر يعيد بناء اتجاه من النسخة الجديدة. الموافقة القديمة تخص قرارًا تاريخيًا، ويجب أن تتوقف صلاحيتها للاستخدام الحالي بمجرد تبدل نسخة البروفايل.

النطاق هو الرحلة الكانونية عبر PostgreSQL، من حفظ ProfileSnapshot إلى عرض الحالة ثم إعادة SWOT واعتمادها وتوليد استراتيجية واعتمادها وإنشاء عقد بوستر جديد. نستخدم رقم نسخة البروفايل المحفوظ كإشارة عالمية. إعادة الاستكشاف الناجحة تنشئ نسخة جديدة ولو تشابه المحتوى. مقارنة تغير اقتباسات بعينها أو جدولة جلب المصادر خارج هذا النطاق.

نقيس على نفس بيانات الاختبار الخيالية قبل وبعد وفق معايير القبول التالية.

- فشل تحديث البروفايل يبقي النسخة الحالية وسريان القرارات. تحديث ناجح يقفل موافقات النسخ القديمة وتجهيز بوستر جديد منها قبل تسجيل عملية توليد أو حجز. تظل مسودة البوستر التاريخي قابلة للفحص بالمسار المحمي.
- تعرض الشاشة سبب التوقف وأول إجراء صالح، وتستعيد الحالة بعد التحديث. بعد SWOT جديدة وموافقتين بشريتين صريحتين على النسختين الجديدتين، يصدر عقد مربوط بالبروفايل الجديد. الاستراتيجية المحجوبة بسبب نقص الأدلة تظل محجوبة.
- إذا تبدل البروفايل بين قراءة المدخلات وحفظ نتيجة SWOT أو الاستراتيجية، يجب ألا تُنسب النتيجة إلى بروفايل لم تقرأه. يجب أن تستقر المهمة بحالة واضحة ويمكن تشغيلها من جديد.
- نقيس حالات القبول والرفض، عدد العمليات والطلبات المدفوعة، وزمن التحقق. الهدف صفر طلبات مدفوعة في التجربة، مع استخدام PostgreSQL وChromium حقيقيين وأدلة ومخرجات مزود مصطنعة صراحةً. جودة النماذج والقدرة على استرداد اقتباسات جديدة من مواقع حية غير مقاستين.

## النسخة ورحلة المنتج

فحصنا النسخة المفتوحة `adarchitect-backend` عند `e1c0504`، وفيها 394 ملفًا بتغييرات مُرحّلة للـindex وملفات أخرى محلية. نقطة الانطلاق للتنفيذ والقياس هي `73399a50d32c683c2d78a72c3eb924bdfa89e35d` من `origin/main` المطابق لـ[المستودع المرجعي](https://github.com/asmaasamyhagag22-design/adzy)، في worktree مستقلة. طابقنا بصمتي حالة وindex النسخة المفتوحة بعد الشغل.

- إدخال URL في Discover يستدعي `POST /api/scrape`، ثم `api/jobs/runner.py` للكشط والاستخراج. يتاح إثراء البروفايل بالموديل حسب الإعدادات. عند النجاح يحفظ PostgreSQL البروفايل والـRun ونتيجة المهمة في معاملة واحدة.
- تسترجع SWOT البروفايل وإشارات السوق والمواد المحفوظة، وقد تستخدم collectors وموديلًا حسب الإعدادات. يحفظ الخادم SWOT ثم يراجعها المستخدم ويعتمد رقم الـRun المعروض.
- `POST /api/strategy/generate` يستخدم الهدف الصريح ومواد البراند وSWOT، وينفذ تقييم كفاية الأدلة والمقترح والتحقق محليًا. تحفظ نتيجة القرار في Run مستقل. يوقف LangGraph الرحلة للمراجعة في SQLite، وتظل موافقة PostgreSQL هي سلطة إصدار عقد الإبداع.
- `POST /api/generate` يجمع عقد الاستراتيجية مع مسار البوستر وفحوصه. تسجل العملية الحجز والمحاولة ثم تحفظ الـAsset والتقييمات. التنزيل المحمي يعيد تقييم صلاحية الموافقة والنسخة والـchecksum.
- شُغلت الرحلة الأساسية في Chromium على `73399a5` بواسطة `tools/verify_copy_editor_browser.py`. بدأت ببروفايل وSWOT مزروعين لبراند خيالي، ثم شغّلت المراجعة والبوستر والتعديل والتنزيل والاستعادة بعد إعادة تشغيل الخادم. رندر التركيب محلي وفحوص المزود اصطناعية. سجل التشغيل أكد صفر dispatches وصفر أخطاء صفحة.

## الفجوات واختيار النطاق

| الفجوة | الدليل وأثره | الاعتماد الخارجي |
|---|---|---|
| تبدل البروفايل يترك قرارات قديمة قابلة للاستخدام | تشغيل HTTP على الأساس أعاد 200 لخمسة طلبات قديمة بعد تبدل البروفايل. تجهيز بوستر دخل مسار الرندر وسجّل عملية، بينما يشترط مسار التنزيل النهائي تطابق البروفايل. كذلك أُلصق خرج مهمتين جاريتين بالبروفايل الجديد. | إصلاح دورة الاعتماد واختبارها يستخدمان PostgreSQL وبيانات خيالية. جمع المادة الجديدة في الواقع يعتمد على توفر الموقع. |
| قرار البحث الموجه بالفجوة يتوقف عند التوصية | `strategy/positioning/research.py` ينتج `COLLECT_SPECIFIC` وقواعد التوقف. `renderApproval` في الواجهة يعرض فحوصًا ويطلب إعادة إدخال أدلة. مسار التوليد يقرأ الأدلة المخزنة. المستخدم يعيد دورة جمع عامة حتى عندما تكون الفجوة محددة. | يحتاج موصل جمع محدود، مصادر متاحة وميزانية واضحة إذا استعان بمزود مدفوع. |
| تعديل النص يفقد إمكانية الوصول إلى إصدار نهائي من الواجهة | رحلة محرر النسخة المرجعية أعادت `NOT_CHECKED` للنسخة المعدلة. يعرض المحرر المسودة ويقفل التنزيل النهائي حتى تحصل الصورة الجديدة على مراجعتها الخاصة. المستخدم يقدر يصلح النص ويحفظه كمسودة. | يحتاج مسار مراجعة بصرية مفوض لبايتات الصورة المعدلة ومزودًا متاحًا للتجربة الحية. |

اخترنا تبدل البروفايل لأن العيب أعاد فتح صلاحيات استخدام محتوى قديم ودخل مسار رندر في حالة قابلة للتكرار، ولأن نتيجة الإصلاح قابلة للفحص من الواجهة إلى قاعدة البيانات محليًا.

## التجارب والقرار

| تجربة | قبل | بعد |
|---|---|---|
| بروفايل جديد بعد اعتماد الاستراتيجية، حالة خيالية واحدة | 5 من 5 طلبات قديمة أعادت 200. سُجلت عملية بوستر واحدة ووصلت مرة إلى بديل الرندر المحلي بحجز مؤقت مقاس قدره 0.60 دولار. بلغ الحجز بعد انتهاء الاختبار صفرًا. | 5 من 5 أعادت 409. صفر عمليات بوستر وصفر دخول للرندر وصفر حجز في هذه الحالة. سِجل الموافقة الأصلية محفوظ. |
| استبدال البروفايل بعد الحساب وقبل حفظ التحليل، حالتان في مهمتي SWOT والاستراتيجية | 2 من 2 انتهت بنجاح ظاهري مع Run جديد على بروفايل مختلف. | 2 من 2 انتهت برسالة تطلب إعادة التحليل. بقي آخر Run صالح للقراءة التاريخية. |
| استئناف قرار معلّق بعد تحديث ناجح | القياس الأساسي غطى حالة قرار معتمد بالفعل. | حالة واحدة أعادت 409، وصفر موافقات على الطلب المعلّق. |
| إعادة التوليد ببروفايل يخلو من دليل «سبب التصديق» | غير مقاس في الأساس. | حالة واحدة أنتجت مقترحًا محجوبًا، ورفض API اعتماده. |
| رحلة الواجهة بعد تحديث ناجح، براند خيالي واحد | تجربة المقارنة الأساسية ركزت على استجابات الخادم. | تحديث فاشل حافظ على الاعتماد. تحديث ناجح طلب المراجعة بعد إعادة التشغيل. الـPNG التاريخية بقيت مسودة بنفس البصمة. موافقتان صريحتان أنتجتا عقدًا من البروفايل الجديد والاقتباس المعدّل. |

أعاد أول قياس للقبول 503 بسبب غياب إعداد الحجز في بيئة الاختبار. أُعيد القياس بحجز اختباري قدره 0.60 دولار وبديل للرندر حتى يصل الطلب إلى بوابة قبول العملية.

الفرضية الأولى كانت أن ربط الصلاحية بمُعرّف البروفايل الحالي يمنع استخدام النسخة القديمة عبر جميع نقاط دخول البوستر. أضفنا الشرط إلى القراءة وقرار الاعتماد وقبول عقد البوستر، وربطنا حفظ المهام بنسخة المدخلات التي قرأتها فعليًا. فشلت المقارنات الثلاث الأساسية قبل التغيير في 13.43 ثانية، ثم نجحت بعده في 13.07 ثانية. الزمن زمن تحقق اختبار بنفس البيئة، وقياس أداء تشغيل المنتج غير مقاس.

الفرضية الثانية كانت أن المستخدم يستطيع الاستئناف من نفس الواجهة. أول تجربة متصفح وصلت إلى اعتماد SWOT جديدة ثم توقفت لأن زر توليد الاستراتيجية ظل معطلًا لو انتقل المستخدم أثناء اكتمال اعتماد SWOT. أعدنا رسم حالة الزر عند اكتمال العملية، ثم نجحت إعادة التجربة. الفحص اللاحق تحقّق من رسالة بطاقة البراند أيضًا. أحدث رحلة استغرقت 45.69 ثانية شاملة التجهيز المحلي وإعادة تحميل المتصفح وإعادة تشغيل الخادم، بعملية بوستر اصطناعية واحدة قبل التحديث وصفر سجلات dispatch. تمت معاينة اللقطتين، وعرض الصفحة على 390 بكسل من غير تجاوز أفقي.

حد السياسة الحالية هو هوية نسخة البروفايل. حتى إعادة حفظ نفس محتوى البروفايل تتطلب المراجعة، وهي حالة المقارنة الأولى. SWOT قديمة بلا رابط إلى بروفايل حالي تتطلب إعادة توليد عند وجود بروفايل محفوظ، وتبقى صفوفها الأصلية في قاعدة البيانات. حجب القبول يطبق عند طلب عملية بوستر جديدة، والعمليات المقبولة سابقًا تخضع لمسارها وسجلها القائمين. فحص المصادر دوريًا، مقارنة الاقتباسات على مستوى الصفحات، معالجة تبدّل SWOT على نفس البروفايل، جودة استراتيجية على مواقع جديدة، وجودة مزود حي غير مقاسة هنا.

## إعادة التشغيل

نفّذي من جذر worktree بعد تجهيز Python 3.12 واعتماديات `requirements-app.txt` وChromium لـPlaywright وصورة Docker `postgres:16-alpine`. برنامج التحقق يستخدم خادمًا محليًا وبيانات خيالية، ويوقف الحاوية المؤقتة عند الانتهاء.

```bash
python -m workflows.verify -q tests/test_profile_refresh_review.py
run_dir=$(mktemp -d)
python tools/verify_profile_refresh_browser.py --directory "$run_dir/demo" --evidence-dir "$run_dir/evidence"
```

لإعادة قياس الحالات الثلاث على المصدر قبل التعديل، نفّذي من الفرع الذي يحتوي هذا التغيير. خروج pytest بحالات فاشلة هو النتيجة المتوقعة على الأساس.

```bash
base_dir=$(mktemp -d)
git worktree add --detach "$base_dir/before" 73399a5
git show HEAD:tests/test_profile_refresh_review.py > "$base_dir/before/tests/test_profile_refresh_review.py"
(cd "$base_dir/before" && python -m workflows.verify -q tests/test_profile_refresh_review.py -k 'blocks_old or cannot_commit_as_new')
```

## اختبارات التوافق وحدودها

- 92 اختبار Python ناجحة في المجموعة المركزة التي تضم الحالات الخمس الجديدة وكفاية البحث وعقد البوستر وSSRF واعتماد SWOT. استُبعد اختبار benchmark واحد بعد أن فشل على الأساس بسبب غياب ملف `outputs/buffaloburger_com_result.json` من checkout العام.
- 9 اختبارات PostgreSQL نجحت لتوافق اعتماد SWOT وتعارض النسخ، ونجح اختبارا HTTP للصلاحيات. أُضيفت للـfixtures الإيجابية روابط البروفايل التي ينشئها مسار التطبيق، مع إبقاء شروط النتائج الأصلية. تشغيل خدمة التخزين الأوسع سبق تحديث تلك الـfixtures وأعطى 41 نجاحًا و3 إخفاقات. نجح الاختباران المرتبطان بربط البروفايل عند إعادتهما في المجموعة المركزة. أعاد اختبار اتجاه استيراد `db` الإخفاق على الأساس أيضًا بسبب استيرادات API موجودة في وحدات البوستر.
- عبور الاستراتيجية عبر PostgreSQL أعطى 6 نجاحات وإخفاقًا واحدًا على الأساس وبعد التعديل. رفض مترجم عقد البوستر نفس مواد fixture لغياب إسناد المصدر المطلوب.
- 21 اختبارًا للمراجعة، و7 لتكامل التطبيق مع LangGraph، و12 للتسليم، و15 لمحرر البوستر، و36 لمسارات المهمة والتحليل والبراند والصرف، و21 اختبار Node، و3 لفحص حزمة المصدر. نجحت أيضًا 11 حالة HTTP مع PostgreSQL و9 حالات لتركيب معاملات حفظ التحليل. كل الأعداد تخص التشغيلات المذكورة على حدة. الاختبار الكامل للمشروع غير مشغّل.
